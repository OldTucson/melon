# melon 主色色卡与配色搜索设计

- 日期：2026-10-22
- 状态：已由用户确认，可进入实施计划
- 目标版本：现有以图搜图能力的增量功能

## 1. 背景与目标

melon 图库需要为每张可预览图片提取并展示 3～5 个主色。用户点击任意色块即可开始配色搜索，并可继续选择多个色块；结果按照整组配色的接近程度排序，允许个别颜色缺失或颜色占比不同。

本功能沿用现有视觉索引 worker、租户隔离、图库筛选和结果卡片，不建立第二套异步任务系统。

成功标准：

- 每张索引就绪的可预览图片稳定展示 3～5 个可点击主色色块。
- 点击一个色块立即进入配色搜索；可继续添加、移除或清空颜色，最多选择 5 色。
- 多色结果按整组感知颜色接近程度稳定排序，而不是把颜色作为严格的 AND 条件。
- 当前文件夹、标签、收藏、格式、授权等图库筛选继续生效。
- 预览替换、索引失败、服务不可用和快速连续点击不会产生旧色卡、越权结果或乱序覆盖。

## 2. 范围与非目标

### 2.1 范围

- 在网格卡片、列表卡片和单图检查器中展示已发布色卡。
- 在现有 Python visual-search worker 中确定性提取主色。
- 在 PostgreSQL 中随视觉索引文档保存版本化色卡。
- 新增独立的配色搜索 API、前端查询状态和结果界面。
- 对现有可索引图片重建索引，补齐色卡。
- 提供提取、存储、排序、接口、交互、无障碍和响应式测试。

### 2.2 非目标

- 不提供任意颜色选择器、手输 HEX 或吸管工具；查询颜色只来自图片色卡。
- 不允许编辑自动提取的主色。
- 不把配色搜索和上传图片搜索组合成同一个查询；开始其中一种搜索会退出另一种。
- 不按颜色名称、色系标签或人工色彩分类搜索。
- 不调用第三方提色或颜色搜索服务。
- 不在浏览器中临时提色或只搜索当前已加载分页。

## 3. 已确认的用户体验

### 3.1 色卡展示

每张卡片在图片、文件信息和操作区之间保留一行固定高度的色块。已发布色卡按颜色占比从高到低排列，数量为 3～5；色块使用等宽布局，避免占比过小的颜色无法点击。颜色占比不通过宽度表达。

每个色块是原生按钮，具有可读的颜色值标签和 `aria-pressed` 状态。选中的颜色显示高对比焦点环，不能只依赖颜色表达选中状态。点击色块不得触发卡片检查器、预览或复选框选择。

检查器使用同一 `PaletteSwatches` 组件的较大尺寸，并显示 HEX 与占比；卡片仅显示色块，保持图库密度。

索引尚未完成时保留同样高度的 5 段中性占位，避免卡片跳动。失败状态显示禁用色卡行和 tooltip“色卡提取失败”；重试仍从现有图像搜索索引设置入口执行。

### 3.2 配色查询

第一次点击色块时：

1. 保存进入搜索前的筛选、排序、滚动、选择和检查器状态。
2. 退出正在进行的上传图片搜索。
3. 以点击颜色创建配色搜索会话并立即查询。

搜索期间在图库工具栏下方显示固定查询条，包含：

- “配色搜索”标题。
- 当前已选的 1～5 个色块。
- 每个颜色的移除按钮。
- “清除配色”操作。
- 结果数量、加载状态或内联错误。

用户可点击任意结果卡片上的色块继续添加颜色，或再次点击已选色块将其移除。完全相同的 HEX 只保留一次；达到 5 色后忽略第六个颜色，并通过 `aria-live` 提示“最多选择 5 个颜色”。颜色变化后等待 150 ms 发起查询，并取消上一请求。

移除最后一个颜色或点击“清除配色”会退出配色搜索并恢复搜索前工作区。开始上传图片搜索同样会先退出配色搜索。配色查询不写入 URL、搜索历史或本地持久化存储。

### 3.3 结果

结果复用现有图库卡片和检查器，按配色距离从近到远显示，最多 30 项，不分“原图/相似图”组，也不向用户展示模型分数。现有图库筛选始终应用；配色搜索期间原有排序控件不可改变匹配度排序。

没有结果时保留查询条并显示“没有找到接近这组配色的图案”。后续颜色调整失败时保留上一批成功结果并显示错误；首次查询失败时恢复普通图库并显示可重试提示。

## 4. 总体架构

```text
预览资产就绪
    │
    ▼
现有 visual-search job / worker
    ├─ 现有：向量、感知哈希、局部特征
    └─ 新增：透明感知的 3～5 色 palette
              │
              ▼
    同一数据库事务原子发布
              │
       ┌──────┴─────────┐
       ▼                ▼
Pattern DTO 色卡    /api/palette-search
       │                │
       ▼                ▼
卡片与检查器       当前筛选 → 精确配色排序
                        │
                        ▼
                  排名后的 Pattern DTO
```

Next.js 仍是唯一公网授权边界。浏览器只向 Next.js 发送颜色与现有筛选；Next.js 从登录会话取得 `ownerId`，解析允许的 Pattern ID，再调用只监听内部地址的 Python 服务。Python 服务不复制文件夹、标签、收藏、授权或回收站规则。

色卡与向量属于同一个索引版本和视觉文档。搜索与普通列表只读取 `ready` 文档，绝不读取 `indexing` 半成品。预览图、算法或索引版本变化时，旧色卡不会与新预览混用。

## 5. 主色提取

新增纯计算模块 `palette.py`，输入规范化的 sRGB 像素和可选 alpha 权重，输出 3～5 条不可变色卡记录。模块不访问数据库、OSS 或网络。

提取流程：

1. 沿用现有安全解码、EXIF 方向和 ICC 到 sRGB 转换，但在透明合成前保留 alpha 通道供色卡使用。
2. 对有透明通道的图片忽略 alpha 小于 16 的像素，其余像素按 `alpha / 255` 加权，减少抗锯齿边缘污染；可见像素不足时回退到现有确定性背景合成结果。
3. 按固定网格确定性采样，最多取 16,384 个像素，避免大图占用过多 CPU 和内存。
4. 将 sRGB 转为 OKLab，用 OpenCV `kmeans` 以固定随机种子聚成 5 类。
5. 按覆盖率降序排列。只要仍多于 3 类，就合并 OKLab 距离小于版本化阈值的近似类。
6. 若源像素只能产生 1～2 个可区分的显示色，则围绕占比最高颜色的 OKLab `L` 生成 `-0.03`、原值、`+0.03` 的在色域明暗层次；若量化后仍重复则改用 `±0.06`。被拆分颜色的覆盖率平均分配给这些层次。该回退只用于满足完全纯色或近单色图片的三色展示约束。
7. 输出始终为 3～5 个互不重复的显示色。将聚类中心转换为大写 `#RRGGBB`，将覆盖率重新归一化为总和 1；相同覆盖率按 HEX 稳定排序。

固定采样、随机种子、合并阈值、色彩转换和透明处理都属于索引版本契约。任何会改变输出的修改必须升级索引版本并回填，不能静默改变已有色卡。

## 6. 数据模型与发布

新增 `visual_search_palette_colors`：

- `document_id UUID NOT NULL`
- `owner_id UUID NOT NULL`
- `pattern_id UUID NOT NULL`
- `color_index INTEGER NOT NULL`，范围 `0..4`
- `display_hex TEXT NOT NULL`，格式为大写 `#RRGGBB`
- `oklab_l REAL NOT NULL`
- `oklab_a REAL NOT NULL`
- `oklab_b REAL NOT NULL`
- `coverage REAL NOT NULL`，范围 `(0, 1]`

约束与索引：

- 主键为 `(document_id, color_index)`。
- `(document_id, owner_id, pattern_id)` 复合外键指向 `visual_search_documents`，删除文档时级联删除色卡。
- 建立 `(owner_id, pattern_id)` B-tree 索引，支持按允许 ID 批量读取。
- publication 层验证每个文档恰有 3～5 条、索引连续、数值有限、HEX 合法且覆盖率总和在浮点容差内为 1。

worker 在生成现有向量和局部特征的同一轮解码中生成色卡。`Repository.publish` 在一个事务中删除目标文档旧 embedding 与 palette 行、插入全部新记录，再将 document 标为 `ready`。任一色卡校验或写入失败都会回滚整个发布并沿用现有 job 重试；单张色卡失败不修改 `patterns.status` 或 `preview_status`。

Pattern 列表仓储层批量关联当前活动版本的 `ready` document，并聚合返回有序色卡，禁止逐卡查询。公开 `PatternItem` 增加：

```ts
type PatternPaletteColor = {
  hex: string;
  coverage: number;
};

type PatternItem = {
  // existing fields
  paletteStatus: "pending" | "ready" | "failed";
  palette: PatternPaletteColor[];
};
```

`paletteStatus=ready` 必须对应 3～5 条记录；其他状态的 `palette` 必须为空数组。

## 7. 配色匹配

当前图库上限低于 10,000 张，每张最多 5 色，因此 MVP 对筛选范围内最多约 50,000 条颜色做精确扫描，不新增近似颜色索引。数据库按 `ownerId + allowedPatternIds + activeIndexVersion + ready` 一次批量读取色卡，Python 用 NumPy 分组计算距离。

查询颜色在服务端转换为 OKLab。对查询集合 `Q` 和候选色卡 `C` 计算：

- `queryCoverage`：每个查询色到候选中最近颜色的 OKLab 距离均值；查询色权重相同。
- `candidateFit`：候选每个颜色到查询中最近颜色的距离，按候选覆盖率加权求和。
- 最终距离：`0.8 * queryCoverage + 0.2 * candidateFit`，越低越接近。

这个双向距离让每个已选颜色都影响结果，同时只轻量惩罚候选中的额外颜色。颜色缺失产生较大最近邻距离，但不会被硬过滤；颜色比例只影响 20% 的候选侧项，符合“允许比例不同”的产品语义。

使用版本化 `palette-scoring-v1.json` 保存最大返回距离、数值归一化参数和并列容差。初始值通过固定质量样本校准并随测试提交。超过最大距离的候选不返回；其余按最终距离、`patternId` 稳定排序，截取前 30 项。

## 8. API 契约

### 8.1 公网接口

`POST /api/palette-search`，`application/json`：

```json
{
  "requestId": "00000000-0000-4000-8000-000000000000",
  "colors": ["#285947", "#CC9C3F", "#8F4038"],
  "filters": {}
}
```

约束：颜色必须是 1～5 个互不重复的大写六位 HEX；`filters` 复用以图搜图允许的图库筛选 schema；未知字段拒绝。Next.js 从会话获得 owner，解析当前筛选允许的 Pattern ID，最多 10,000 个。

成功响应：

```json
{
  "query": { "colors": ["#285947", "#CC9C3F", "#8F4038"] },
  "items": [],
  "timing": { "totalMs": 84 }
}
```

`items` 是按内部距离排序、带色卡的现有 Pattern DTO。公开响应不包含 OKLab、内部距离、阈值或索引文档 ID。

公开错误码：

- `PALETTE_SEARCH_INVALID_COLORS`：数量、格式或重复值不合法。
- `PALETTE_SEARCH_NO_INDEX`：当前筛选范围没有已就绪色卡。
- `PALETTE_SEARCH_TIMEOUT`：搜索超时。
- `PALETTE_SEARCH_UNAVAILABLE`：内部服务或响应不可用。

### 8.2 内部接口

Python 服务新增 `POST /internal/palette-search`，沿用现有 Bearer token、请求 ID、owner ID 和允许 Pattern ID 约束。内部响应只包含排名所需 Pattern ID 和距离；Next.js 必须验证所有返回 ID 均在允许集合中，再按同一 owner 回填 DTO。

客户端、Next.js 内部调用和 Python 查询都支持取消。新的颜色请求开始后，旧请求即使完成也不得覆盖新状态。

## 9. 前端组件边界

- `PaletteSwatches`：只负责渲染 3～5 个颜色、选中态、键盘操作和点击事件；不知道搜索 API。
- `PaletteQueryBar`：展示已选颜色、加载/错误/数量状态以及移除、清空操作。
- `PaletteSearchResults`：复用 `PatternCard` 展示有序结果和空状态。
- `usePaletteSearchSession`：负责工作区快照、颜色集合、150 ms 防抖、AbortController、结果保留和退出恢复。
- `palette-search/contracts.ts`：共享 Zod 请求、响应和错误边界。
- `palette-search-service.ts`：服务端解析允许 Pattern ID、调用内部服务并回填 Pattern DTO。

`library-view.tsx` 只协调普通图库、以图搜图和配色搜索三种互斥模式，不直接实现配色打分或请求细节。新增状态放入专用 hook，避免继续扩大现有图片搜索会话逻辑。

色卡交互支持鼠标、触控和键盘。移动端色块保留约 44 px 的有效点击区域，视觉色块可以较小；查询条允许换行，不产生横向滚动或遮挡。

## 10. 生命周期、开关与回填

色卡依赖现有 visual-search 服务，继续由 `IMAGE_SEARCH_ENABLED` 控制，不新增第二个功能开关。关闭时不渲染色卡搜索交互，普通图库不受影响。

首次实现会提升视觉索引版本，因为旧 `ready` 文档没有满足发布契约的色卡。部署顺序：

1. 应用数据库迁移和可同时读取旧文档的代码。
2. 启动支持新版本的 API 与 worker。
3. 使用现有重建入口为所有可索引图片创建新版本 job。
4. 等待新版本完成，并处理明确失败项。
5. 切换活动版本；卡片与搜索同时开始读取新色卡。

回填期间旧版本继续提供现有以图搜图，不展示不完整色卡。预览替换会创建新 job；新文档发布前不再返回旧预览的色卡。永久删除沿 document 外键级联清理 palette，不产生新的 OSS 对象。

## 11. 错误处理与安全

- 提色异常使用稳定内部错误码，沿用最多 5 次退避重试；确定性数据错误最终标记 job 失败。
- 搜索服务离线时已发布色卡仍可显示，但点击搜索会给出可重试错误，普通文字搜索、上传、下载和图库浏览保持可用。
- 快速添加或移除颜色只接受最新 request ID 的响应。
- Next.js 不信任浏览器或 Python 返回的 owner、Pattern ID 或颜色格式；所有结果二次校验所有权与允许集合。
- 日志只记录 request ID、颜色数量、允许 Pattern 数、候选数、耗时和稳定错误码，不记录长期用户查询历史。
- 色卡只来自用户已有预览，不增加浏览器 OSS 权限，也不产生新的服务端派生文件。

## 12. 测试与验收

### 12.1 Python 单元与集成测试

- 固定图片多次提取产生完全一致的 HEX、顺序和覆盖率。
- 覆盖透明背景、半透明边缘、完全纯色、近单色、低对比、高饱和和不足可见像素回退；纯色回退的 `L` 偏移与覆盖率分配必须符合固定规则。
- 任意合法图片产生 3～5 个非重复 HEX，覆盖率有限且总和为 1。
- 精确同色候选优先于轻微色差，轻微色差优先于缺色，缺色优先于无关配色。
- 改变颜色比例只轻量影响排序；查询色缺失产生明显惩罚但不硬过滤。
- publication 对缺色、超量、非法数值、非连续索引和错误 owner 拒绝并完整回滚。
- 配色读取与搜索验证租户隔离、活动版本、允许 ID 和稳定并列排序。

### 12.2 Next.js 与组件测试

- Pattern DTO 聚合不会产生 N+1 查询，状态与色卡数量保持一致。
- API 拒绝未登录、跨站、空颜色、超过 5 色、重复值、非法 HEX、未知字段和越权内部结果。
- 色块点击不会触发卡片其他交互；支持添加、重复移除、单独移除、清空和 5 色上限。
- 搜索继承全部允许筛选，结果保持服务端排名。
- 新请求取消旧请求；错误保留上一成功结果；退出恢复搜索前工作区。
- 配色搜索与以图搜图互斥切换，不残留 Blob、选择或结果状态。
- 网格、列表、检查器和移动端布局无文字溢出、遮挡或布局跳动，键盘和读屏状态可用。

### 12.3 端到端验收

在真实本地图库完成索引重建后验证：

- 所有可索引且新版本 `ready` 的图片都展示 3～5 个色块。
- 更换手动预览后色卡随新文档更新，不短暂回退到旧色卡。
- 选择一色、三色和五色均能得到稳定结果，完全或近似整组配色排在缺色和无关配色之前。
- 文件夹、标签、收藏和格式筛选不会泄露范围外图案。
- 10,000 张、每张 5 色的合成基准在生产同规格 ECS 上，配色搜索 API P95 不超过 1 秒。
- 现有图片搜索 Python 测试、Next.js 类型检查、lint、组件测试和 Playwright 冒烟测试继续通过。

## 13. 明确决策

- 采用独立、持久化的色卡索引，而不是把纯色拼图交给视觉模型或在浏览器端即时比较。
- 点击图片色块直接搜索，不增加独立颜色选择器。
- 支持最多 5 色，按整组配色距离排序，不要求同时严格命中全部颜色。
- 查询颜色权重相同，候选原始占比仅通过 20% 的候选侧距离轻量影响结果。
- 当前规模使用精确扫描；只有实际容量或基准证明需要时才引入颜色 ANN 索引。
- 配色搜索与以图搜图互斥，但都继承当前图库筛选。
