# 上传处理中状态恢复设计

日期：2026-10-15

## 背景

图库当前把两种不同情况合并成了同一个错误：

- 选中的图案已经不在当前结果中，属于真正的“选择已变化”；
- 图案仍然存在，但上传状态是 `processing`，正常操作需要暂时锁定。

因此，正在完成上传的图案会显示“选择已变化，请刷新后重新选择”，而且所有操作均不可用。提示与真实状态不符，也没有提供安全的恢复入口。

## 目标

- 准确区分“选择失效”和“上传处理中”。
- 上传正常进行时不增加轮询。
- 仅在用户选中异常停留在处理中状态的图案时，定向查询该图案状态。
- 上传完成请求中断后，可以复用原请求安全恢复，不重复上传 OSS 文件。
- 数据库、网络或 OSS 暂时不可用时，给出明确状态，不误导用户反复操作。

## 非目标

- 本次不引入 WebSocket、SSE 或后台任务系统。
- 本次不轮询整个图库列表。
- 本次不放开处理中图案的编辑、移动、收藏、授权或删除操作。
- 本次不改变 OSS、STS 或 RAM 配置。

## 采用方案

### 1. 状态与提示分离

批量操作栏和右侧检查器分别判断：

- `selectedIds` 中存在查不到的 ID：显示“选择内容已变化，请重新选择”，提供“清除选择”。
- 图案状态为 `draft`、`hashing`、`uploading` 或 `processing`：显示“图案正在完成上传”，普通操作保持禁用。
- 状态查询失败：显示“状态暂时无法更新”，保留手动“重新检查”。
- 图案进入 `ready` 或 `failed`：停止状态刷新，并恢复该状态原本允许的操作。

`processing` 是合法的暂态，不再被描述成选择失效。

### 2. 定向自适应刷新

正常上传由上传请求的返回结果直接更新缓存，不启动定时刷新。

仅当用户当前只选中一个暂态图案，且该图案没有被本地上传流程主动推进时，查询 `GET /api/patterns/:id`：

- 发现后的前 30 秒：每 5 秒一次；
- 超过 30 秒：每 15 秒一次；
- 页面进入后台、浏览器离线、取消选择、状态变为 `ready`/`failed` 时停止；
- 请求失败沿用查询层的有限重试，随后进入 15 秒节奏，不形成紧密重试循环；
- 用户可以点击“重新检查”立即发起一次查询。

查询只返回单个图案。状态变化后仅刷新受影响的图案缓存和当前图库查询，不请求无关资源。

### 3. 完成阶段的幂等恢复

服务端现有上传完成接口已经支持同一 `sessionId`、`operationId` 和相同资源声明的幂等重放。客户端恢复必须复用这套协议，而不是重新初始化上传。

客户端在第一次调用完成接口前，将以下非敏感信息写入 IndexedDB 上传检查点：

- `sessionId` 与 `operationId`；
- 源文件、预览图和缩略图的 `assetId`、`kind`、`objectKey`、`extension`、`sizeBytes`、宽高；
- `completionStartedAt`。

不持久化 STS 凭证、AccessKey、文件内容或 Blob。

恢复时：

1. 读取检查点中的原始资源声明；
2. 直接重放完成请求；
3. 跳过哈希、初始化和 OSS 上传；
4. 成功后删除检查点、更新图案缓存并关闭恢复状态；
5. 若服务端返回终态冲突，停止自动恢复并显示可操作错误。

检查点字段为可选字段，兼容现有记录，无需修改 IndexedDB 索引。旧记录若只有源文件且没有衍生资源，可以由现有源文件元数据恢复；无法完整还原声明的旧记录不做猜测，要求重新选择原文件或人工处理。

### 4. 恢复入口

图案连续处于 `processing` 超过 30 秒后：

- 图库检查器显示“重新检查”；
- 对应上传任务存在可重放检查点时，上传队列显示“恢复上传”；
- 没有完整检查点时，不显示会重复初始化的“重试”，而是保留重新选择原文件的入口；
- “放弃上传”仍是独立的破坏性操作，不能作为默认恢复路径。

点击恢复期间按钮禁用，避免同一客户端重复提交。即使发生并发重放，服务端幂等约束也保证只生成一次完成结果。

## 数据流

```text
本地上传成功
  -> 保存精确 completionAssets 检查点
  -> POST complete
     -> 成功：ready + 清理检查点 + 刷新缓存
     -> 网络中断/超时：保留 processing + 检查点
        -> 30 秒后提供恢复
        -> 使用相同 payload 重放 complete

用户选中 processing 图案
  -> 单图案状态查询（5 秒，随后 15 秒）
  -> ready/failed：停止刷新并同步当前图库
  -> 请求失败：显示服务暂不可用，可手动重新检查
```

## 错误处理

- 数据库或 API 不可用：显示“状态暂时无法更新”，不改写为选择失效。
- OSS 校验仍在进行：保持 `processing`，继续低频定向查询。
- 完成请求网络超时：保留检查点，允许幂等恢复。
- 完成 payload 与既有请求不一致：停止恢复并提示需要重新选择原文件或人工检查，禁止生成第二套声明。
- 图案已删除或不在当前用户下：按真正的选择失效处理并清除选择。

## 测试策略

- 组件测试：选择失效、处理中、查询失败三类提示互不混淆；暂态图案操作保持禁用。
- 查询测试：5 秒/15 秒节奏、终态停止、取消选择停止、后台和离线停止、手动重新检查。
- 上传运行器测试：完成前写入精确声明；恢复仅调用 `complete`，不调用初始化、哈希或 OSS 上传。
- 检查点测试：新字段持久化；旧记录可读取；不保存凭证或 Blob。
- 服务集成测试：同 payload 并发重放只产生一个完成结果和一条变更记录。
- 回归测试：正常上传仍由直接响应更新，不产生额外轮询；`ready` 和 `failed` 图案现有操作不受影响。

## 验收标准

- 选中 `processing` 图案时不再出现“选择已变化”。
- 用户可以看到真实上传状态，并能手动检查。
- 正常上传路径没有定时请求。
- 异常停留的选中图案最多每 5 秒请求一个单图案接口，30 秒后降为每 15 秒。
- 恢复完成阶段不会重新上传文件，也不会创建重复图案或重复变更记录。
- 页面后台或离线时没有状态轮询。
