# melon 以图搜图设计

- 日期：2026-10-20
- 状态：已由用户确认，可进入实施计划
- 目标版本：MVP 增量功能

## 1. 背景与目标

melon 需要在现有私有图库中增加以图搜图。用户上传或粘贴一张模糊、压缩、裁剪或不完整的图片后，系统应优先找回它在图库中的原始图案，并在精准目标之后提供视觉相似图案。

已确认的产品约束：

- 图库规模低于 10,000 张图案。
- “找回同一张原图”优先于泛化的相似推荐。
- 所有检索数据与计算完全自托管，不调用第三方识图服务。
- MVP 复用现有 ECS，允许一次搜索用时约 3-8 秒，不配置 GPU。
- 使用“视觉向量召回 + 局部特征精排 + 感知哈希辅助”的混合检索方案。
- Mac 桌面浏览器优先，同时不阻断后续 iPad 和手机网页适配。

成功标准不是“能返回相似图片”，而是能用真实图库证明局部截图、模糊图和常见转码图的目标找回率，并将仅仅风格相似的结果与可能的原图明确区分。

## 2. 范围与非目标

### 2.1 MVP 范围

- 从 JPG、PNG、WebP、HEIC 或 HEIF 查询图片搜索当前用户自己的图库。
- 支持整图搜索和可选的手动裁剪区域。
- 对 JPG、PNG、PSD、AI、PDF 和 Procreate 图案统一使用已生成的预览图建立索引。
- 返回“高概率原图”“可能是原图”“视觉相似”三类结果。
- 在图片结果上继续使用现有文件夹、标签、格式和授权状态筛选。
- 自动索引新预览、替换后的手动预览和已有图库。
- 在设置页显示索引状态，并允许重试失败项或重建索引。

### 2.2 非目标

- 不训练或微调自有视觉模型。
- 不调用阿里云图像搜索或其他外部视觉 API。
- 不搜索 PSD/AI 图层、PDF 文本、文件名或标签语义；文字搜索仍走现有入口。
- 不保存查询图片、搜索历史或用户裁剪区域。
- 不为回收站、处理中或永久删除的图案返回结果。
- 不承诺找到图库中不存在的“来源图片”。无可靠原图证据时只能归类为视觉相似。
- 不在 MVP 中提供人脸识别、OCR、自动打标或版权互联网反向搜索。

## 3. 总体架构

```text
浏览器
  │  查询图片 + 当前筛选条件
  ▼
Next.js /api/image-search
  ├─ 登录、CSRF、大小与类型校验
  ├─ 用现有仓储层解析当前用户允许搜索的 Pattern ID
  └─ 用内部密钥调用回环地址
          │
          ▼
Python visual-search 服务（仅监听 127.0.0.1）
  ├─ ONNX Runtime：DINOv2 视觉向量
  ├─ OpenCV：感知哈希、SIFT 与几何验证
  ├─ PostgreSQL + pgvector：候选召回与任务状态
  └─ OSS：读取预览，保存版本化局部特征文件
          │
          ▼
Next.js 按排名加载 Pattern DTO → 现有图库网格
```

现有 Next.js 应用仍是唯一公网服务与授权边界。Python 服务不是第二个面向用户的后端，不暴露公网端口，也不签发登录会话；它只接受来自 Next.js 的内部请求。

视觉计算与 Next.js 进程隔离，原因是模型推理和 OpenCV 解码属于 CPU、内存密集型工作。索引任务由独立 worker 串行执行，不占用上传请求。生产环境先各运行一个 API 进程和一个 worker 进程，并将索引并发限制为 1；规模或并发增长后再水平拆分，不在 MVP 提前引入 Redis 或消息队列。

建议生产 ECS 至少为 2 vCPU、4 GB 内存。2 GB 实例可以以单并发和较慢回填运行，但上线前必须在真实实例上通过内存与 P95 延迟验收。

## 4. 组件边界

### 4.1 图库客户端

职责：选择、拖入或粘贴查询图；提供可选裁剪；展示搜索阶段、分类结果、错误和退出操作。客户端只保存当前页面生命周期内的 `Blob`，刷新或退出搜索即丢弃。

客户端不计算模型向量，不把查询图写入 Dexie、上传队列、最近使用或 OSS，也不自行决定“原图”置信等级。

### 4.2 Next.js 搜索编排层

职责：

- 验证当前 Auth.js 会话和请求来源。
- 限制请求体、MIME、扩展名和筛选参数。
- 通过现有 Pattern 查询规则生成当前用户、当前筛选条件下可搜索的 Pattern ID 集合；上限为 10,000。
- 调用内部搜索服务并传入 `ownerId`、允许的 Pattern ID、查询图片和请求 ID。
- 忽略内部服务返回的任何越权 ID，按相同 `ownerId` 再次加载 Pattern DTO，并保持内部服务给出的排序。
- 将内部错误映射为稳定的公开错误码，不泄露模型、路径或 OSS 信息。

这一边界避免 Python 服务复制文件夹、标签、授权状态和回收站等业务查询规则。

### 4.3 visual-search 服务

职责：安全解码查询图、提取特征、从专用检索表召回候选、读取候选局部特征、执行几何精排，并返回有序的 Pattern ID、结果类别和内部诊断分数。

服务使用固定且带校验和的 ONNX 模型文件。MVP 的索引版本为 `visual-search-v1`，其模型定义为 DINOv2 ViT-S/14、384 维输出；模型、预处理参数、切片规则、局部描述子和打分配置共同组成索引版本。任何一项发生不兼容变化都必须创建新版本并回填，不能静默复用旧向量。

### 4.4 索引 worker

职责：领取数据库任务、读取目标预览、生成全部索引数据、原子发布新版本、清理被取代的派生特征，并记录可重试错误。worker 与在线搜索使用同一套特征提取代码和模型文件，防止查询与索引预处理漂移。

## 5. 特征与检索算法

### 5.1 索引输入

只对 `previewStatus` 为 `ready` 或 `manual` 且存在 preview 资产的图案建立索引。使用最长边 2048 px 的预览，而不是最大 100-200 MB 的源文件。这样 PSD、AI、PDF 和 Procreate 与位图使用同一检索管线。

预览进入模型前执行 EXIF 方向修正、sRGB 转换、透明背景合成和确定性缩放。透明内容分别在浅灰与深灰背景上评估后固定选择信息量更高的一份，避免透明图案因查询截图背景不同而完全失配。

### 5.2 每张图案的检索数据

- 一个全图 DINOv2 向量，用于整体构图和视觉风格召回。
- 九个 3x3 重叠区域向量，用于只包含局部内容的查询。区域边缘保留重叠，减少目标刚好跨切片边界的漏召回。
- 一个 64 位感知哈希，用于压缩、缩放和轻微亮度变化后的近重复识别。
- 最多 256 个 SIFT 关键点、描述子及坐标，用于候选的局部几何验证。

向量统一做 L2 归一化，使用 cosine distance。局部特征以压缩、版本化文件保存到该图案的 OSS 前缀：

```text
users/{ownerId}/patterns/{patternId}/derived/search/{indexVersion}/{previewHash}.npz
```

该对象仍在现有图案前缀内，因此永久删除图案时的前缀兜底清理可以覆盖它。搜索模块必须增加独立、严格的 key 构造与解析函数，不能让浏览器获得写入该路径的 STS 权限。

### 5.3 查询与候选召回

1. 安全解码查询图并应用与索引相同的标准化。
2. 对整张查询图提取全图向量、局部切片向量、感知哈希和 SIFT 特征。
3. 在 `ownerId` 和 Next.js 给出的允许 Pattern ID 内，用全图及局部向量召回候选并按 Pattern ID 合并。
4. 广泛筛选时使用 HNSW 近似索引；允许集合较小时使用精确 cosine 扫描，避免过滤条件导致近似索引漏召回。
5. 合并后最多保留 50 张候选进入精排。

### 5.4 精排与结果分类

每个候选计算四类证据：全图向量相似度、最佳局部向量相似度、感知哈希距离、SIFT 匹配经 RANSAC 几何验证后的内点数量、比例与覆盖度。

分类规则遵循以下安全边界：

- “高概率原图”必须通过近重复哈希或几何一致性验证，不能只凭视觉向量相似度得出。
- “可能是原图”必须至少存在较弱但有效的哈希或几何证据。
- 未通过同源验证但向量相似的候选只能标记为“视觉相似”。
- 低于版本化最低相似度门槛的候选不返回，避免为了填满结果而展示无关图案。
- 重复纹样容易产生局部误配，因此几何证据必须同时满足最小内点数、内点比例和有效覆盖面积，不能只看匹配点数量。

初始门槛由离线基准工具生成，再作为 `visual-search-v1` 的只读配置提交。生产运行期间不允许无版本变更地手动漂移阈值。最终用户界面不展示原始百分比，以免把模型分数误解为版权或身份确定性。

## 6. 数据模型

### 6.1 PostgreSQL 扩展

迁移启用 `vector` 扩展，并在部署检查中验证版本。开发 PostgreSQL 镜像改为与 PostgreSQL 17 匹配的 pgvector 镜像；生产数据库必须在发布迁移前确认支持 `CREATE EXTENSION vector` 且 pgvector 不低于 0.8.0，以支持带业务筛选的迭代近邻扫描。

### 6.2 `visual_search_documents`

每个预览指纹和索引版本一行，保存：

- 独立 UUID `id` 主键。
- `owner_id`, `pattern_id`, `index_version`, `preview_hash` 复合唯一键。
- `preview_asset_id`, `preview_hash`，用于判断索引是否过期。
- `status`: `pending | indexing | ready | failed | superseded`。
- `phash bit(64)`、原始宽高、局部特征 OSS key。
- `attempt_count`, `last_error_code`, `indexed_at`, `created_at`, `updated_at`。

所有查询都必须带 `owner_id`；外键沿用 `(owner_id, pattern_id)` 复合所有权约束。同一图案可以同时拥有旧模型版本和正在构建的新版本；部分唯一索引约束 `(owner_id, pattern_id, index_version) WHERE status = 'ready'`，保证一个版本只有一个可搜索 document。

### 6.3 `visual_search_embeddings`

每个 document 的全图或切片各占一行：

- `document_id`, `region_index` 复合唯一键；`document_id` 外键级联到 document。
- 冗余保存 `owner_id` 和 `pattern_id`，并用复合外键保证它们与 document 所有权一致，便于强制隔离和过滤。
- `region_kind`: `global | tile`。
- 归一化边界坐标 `x`, `y`, `width`, `height`。
- `embedding vector(384)`。

建立 owner/pattern B-tree 索引和 `vector_cosine_ops` HNSW 索引。删除 document 时级联删除其向量。

### 6.4 `visual_search_jobs`

保存 `job_id`, `owner_id`, `pattern_id`, `preview_asset_id`, 可空的 `preview_hash`, `index_version`, `status`, `attempt_count`, `available_at`, `lease_until`, `last_error_code` 和时间戳。新上传若已有可信内容哈希可以直接写入；历史预览回填时由 worker 下载并计算 SHA-256 后补齐。

`owner_id + pattern_id + preview_asset_id + index_version` 唯一，使用不可变的预览资产身份保证重复上传完成事件或重复回填不会生成重复任务。worker 使用 `FOR UPDATE SKIP LOCKED` 和租约领取任务；进程退出后，过期租约可由下一次轮询恢复。

## 7. API 契约

### 7.1 公网接口

`POST /api/image-search` 使用 `multipart/form-data`：

- `image`: 必填查询图片。
- `filters`: JSON 字符串，复用现有图库筛选 schema 的允许子集。
- `requestId`: 客户端生成的 UUID，用于日志关联和取消旧响应。

成功响应包含：

```json
{
  "query": { "width": 1200, "height": 900 },
  "groups": [
    { "kind": "probable_source", "items": [] },
    { "kind": "possible_source", "items": [] },
    { "kind": "visually_similar", "items": [] }
  ],
  "timing": { "totalMs": 3210 }
}
```

公开响应中的 item 是现有 Pattern DTO 加只读 `matchKind`，不返回内部特征、距离、模型路径或 OSS 特征 key。

稳定公开错误码：

- `IMAGE_SEARCH_INVALID_FILE`：文件类型、签名或尺寸不合法。
- `IMAGE_SEARCH_IMAGE_TOO_LARGE`：编码大小或解码像素超限。
- `IMAGE_SEARCH_NO_INDEX`：筛选范围内没有已就绪索引。
- `IMAGE_SEARCH_BUSY`：在线推理并发已满，可稍后重试。
- `IMAGE_SEARCH_TIMEOUT`：超过 12 秒。
- `IMAGE_SEARCH_UNAVAILABLE`：内部服务不可用。

### 7.2 内部接口

内部服务只监听回环地址，并要求 `Authorization: Bearer {IMAGE_SEARCH_INTERNAL_TOKEN}`、请求 ID、owner ID 和允许 Pattern ID。token 使用常量时间比较，日志不得打印 token 或图片内容。

内部响应可以包含排名诊断分数，但 Next.js 必须丢弃这些字段，不向浏览器透传。接口全链路支持 AbortSignal；用户退出或重新搜索时应尽快中止旧请求。

## 8. 索引生命周期

### 8.1 创建与替换

- 上传完成且 preview 资产可用时，在完成事务内幂等插入索引任务；不得同步运行模型。
- 手动预览完成时，在同一业务事务中替换 preview 资产；旧资产的级联约束会删除其 document、embedding 和待处理 job，同时为新 `preview_asset_id` 创建任务。新索引完成前宁可暂时搜不到该图案，也不能继续匹配已经被替换的旧预览；`superseded` 保留给不删除资产的版本切换流程。
- worker 先写入版本化 OSS 特征对象和未发布的向量，再在一个数据库事务中把 document 标为 `ready`。数据库发布失败时删除新写的特征对象；周期性运维清理命令处理进程崩溃留下的孤立对象。搜索永远不读取半成品。
- 预览生成失败或不支持时不创建任务；后续补充手动预览会正常触发。

### 8.2 回填与模型升级

提供显式运维命令扫描所有可索引图案并幂等创建缺失任务。首次上线和模型版本升级均使用该命令，不在 Web 服务启动时隐式回填。

模型升级与替换预览不同：旧 `ready` 模型版本继续服务，直到新版本完成率达到 100% 或运维人员明确接受失败项后再切换 `IMAGE_SEARCH_ACTIVE_VERSION`。切换后才能清理旧版本，确保回滚只需恢复配置而非重新计算。

### 8.3 回收站和永久删除

- 移入回收站不删除索引；Next.js 的允许 ID 查询会排除该图案。
- 恢复后原索引立即可用，不需要重新计算。
- 永久删除在数据库事务中删除 document、embedding 和待处理 job；现有图案 OSS 前缀清理同时删除局部特征文件。
- 如果 OSS 删除暂时失败，沿用现有清理重试机制，数据库墓碑不能被失败清理复活。

### 8.4 重试

可重试错误采用退避调度，最多自动尝试 5 次。文件确定损坏、预览不存在或尺寸越界属于不可自动重试错误，直接进入 `failed`。设置页“重试失败项”会验证当前预览仍有效后创建新任务，而不是修改历史任务。

## 9. 用户体验

### 9.1 入口与选图

在顶部文字搜索框右侧增加 Lucide 图像搜索图标按钮和 tooltip“以图搜图”。它是搜索工具，不与“上传”主按钮合并。

弹窗支持：

- 点击选择、拖入和从剪贴板粘贴一张图片。
- JPG、PNG、WebP、HEIC、HEIF；编码文件最大 20 MB。
- 最短边至少 96 px，解码后最多 40 MP。
- 可解码时显示预览与可选裁剪框；不裁剪时使用整张图。
- 浏览器不能本地预览 HEIC/HEIF 时仍允许整图提交，但不显示裁剪控件。

点击“开始搜索”后显示稳定的三阶段文案：`分析图片`、`查找候选`、`精确比对`。这些阶段只表达正在工作，不伪造无法从服务端确定的百分比。

### 9.2 结果模式

结果使用现有图库网格，顶部显示查询缩略图、结果数量和“退出搜图”。结果按“高概率原图”“可能是原图”“视觉相似”顺序分组，空分组不显示；没有同源证据时只显示视觉相似结果和明确的未找到原图提示。图片搜索期间排序固定为匹配度，退出后恢复进入搜索前的排序。

搜索前的 URL 筛选、文件夹、排序、滚动位置和已打开检查器状态保存在内存快照中。退出搜图后恢复该快照。刷新页面会结束当前图片搜索，因为服务端不保存查询图。

图片卡片沿用现有交互约束：点击图片区域打开右侧检查器但不改变复选框；点击复选框只改变多选状态；搜索完成不自动打开检查器或自动选择结果。

桌面使用居中弹窗与现有连续工作区。窄屏时选图弹窗转为底部面板，结果仍使用响应式图库网格，不新增独立移动路由。

### 9.3 设置页状态

增加“图像搜索索引”区块，显示当前版本、可索引总数、已就绪、等待中、处理中和失败数量，以及最后一次 worker 心跳。提供“重试失败项”和带二次确认的“重建全部索引”。普通索引进度不占用图库顶部空间。

## 10. 安全与隐私

- 查询图片只存在于浏览器内存、请求流和服务端受控临时文件；成功、失败、取消或超时均在 `finally` 中删除。
- 临时目录使用操作系统安全创建方式、随机文件名、`0600` 权限和独立容量上限；守护清理任务移除异常退出遗留的过期文件。
- 先限制编码字节数，再由解码器限制宽高、总像素、帧数和解码时间，防止压缩炸弹。
- MIME 只作提示，最终以 magic bytes 和实际解码结果为准；不接受 SVG、PDF 或任意归档作为查询图。
- Python 服务不信任浏览器提供的 owner ID 或 Pattern ID。它只接受内部 token；Next.js 从服务端会话产生 owner ID，并在返回时再次校验所有权。
- 搜索与索引日志只记录 request ID、Pattern ID、模型版本、耗时、候选数和稳定错误码，不记录图片字节、局部特征或长期可访问的签名 URL。
- 浏览器 STS 策略不增加搜索特征路径权限。只有 ECS 实例角色可以读写服务端派生的 search 对象。

## 11. 故障处理与可观测性

- 在线搜索总超时为 12 秒；超时后取消下游工作并清理临时文件。
- visual-search 服务不可用时只禁用以图搜图，文字搜索、上传、下载和图库浏览保持可用。
- 单张图案索引失败不会修改 `patterns.status` 或 `preview_status`。
- worker 每个任务提交阶段均幂等；进程崩溃不会留下可被搜索的半成品。
- 指标至少包括搜索总耗时、特征提取耗时、召回耗时、精排耗时、候选数、各结果类别数量、无结果率、任务积压、失败率和 worker 心跳。
- 日志统一携带 request ID 或 job ID。错误页面只显示可操作信息，详细堆栈仅在服务端日志中。

## 12. 性能与容量

按 10,000 张、每张 1 个全图加 9 个局部向量估算，共约 100,000 条 384 维向量。原始 float32 向量约 147 MiB，另加 HNSW、行元数据和局部特征对象，仍适合当前规模的 PostgreSQL 与 OSS。

性能策略：

- 在线查询优先于后台索引；检测到搜索请求时 worker 不增加并发。
- MVP 索引并发固定为 1，在线推理并发有界，超过限制返回可重试的繁忙错误而不是耗尽内存。
- 局部特征只为最多 50 个候选读取，并使用有容量上限的本地 LRU 缓存。
- 现有图案的首次回填允许持续数小时，不作为部署请求的一部分；回填期间已完成的图案可逐步参与搜索。
- 上线前必须在生产同规格 ECS 上测量内存峰值、单张索引耗时和搜索 P95，而不是用开发机结果代替。

## 13. 测试与验收

### 13.1 离线质量基准

从真实图库选取不少于 100 张图案，覆盖照片感、插画、连续纹样、低对比度、透明背景、文字元素和高度相似系列。对每张图自动生成缩放、JPEG 压缩、中等模糊、轻微旋转及多个保留至少 25% 原图内容的裁剪查询，并补充人工截图与图库外负样本。

`visual-search-v1` 必须达到：

- 原图、缩放图和压缩图的 Top 1 找回率不低于 98%。
- 保留至少 25% 内容的局部裁剪，Top 5 找回率不低于 90%。
- 中等模糊截图，Top 5 找回率不低于 85%。
- 图库外负样本被错误归为“高概率原图”的比例低于 5%。
- 同一固定基准与模型文件重复运行时，分类结果可复现。

质量未达到门槛时不得通过放宽“高概率原图”阈值掩盖问题；应调整召回、切片或精排后创建新的配置版本。

### 13.2 自动化测试

- 单元测试：预处理、切片边界、向量归一化、哈希距离、SIFT/RANSAC 打分、分类和稳定错误映射。
- 契约测试：Next.js 与 Python 请求/响应 schema、内部鉴权、取消与超时。
- 数据库集成测试：租约领取、并发 worker、幂等任务、模型切换、owner 隔离、回收/恢复/永久删除和级联清理。
- 服务集成测试：真实测试图片的召回顺序、损坏文件、超像素图片、透明背景和无索引范围。
- 组件测试：选择、粘贴、裁剪、进度、分组结果、空状态、退出恢复和卡片事件互不冒泡。
- Playwright：从图片搜索入口到打开结果检查器的桌面、iPad 宽度与手机宽度主流程。
- 安全测试：跨用户 ID、伪造 MIME、SVG、归档、解码炸弹、内部 token 缺失和临时文件清理。

### 13.3 运行验收

- 生产同规格 ECS 上 P95 搜索响应不超过 8 秒，且进程内存不触发 OOM。
- 搜索完成、失败、取消与超时后均不存在超龄查询临时文件。
- 回填、索引失败或搜索服务停止时，现有图库功能不回归。
- 100% owner 隔离：任何检索路径都不能返回另一个用户的 Pattern ID 或元数据。

## 14. 发布与回滚

功能由 `IMAGE_SEARCH_ENABLED` 控制。发布顺序：

1. 备份数据库并部署 pgvector 迁移。
2. 部署固定模型、Python 服务和 worker，但保持公网功能关闭。
3. 运行质量基准与小批量回填，验证 OSS、内存和索引任务。
4. 回填全部现有可预览图案并检查失败项。
5. 在生产同规格实例完成延迟、隔离和临时文件验收。
6. 打开功能开关。

回滚时先关闭功能开关，再停止 API/worker。新增表和派生 OSS 对象保留以便恢复，不在紧急回滚中执行破坏性降级；确认永久放弃该版本后再通过显式清理命令删除。

## 15. 配置项

生产所需配置：

- `IMAGE_SEARCH_ENABLED`
- `IMAGE_SEARCH_SERVICE_URL`，生产固定为回环地址
- `IMAGE_SEARCH_INTERNAL_TOKEN`
- `IMAGE_SEARCH_ACTIVE_VERSION=visual-search-v1`
- `IMAGE_SEARCH_MODEL_PATH`
- `IMAGE_SEARCH_MODEL_SHA256`
- `IMAGE_SEARCH_TEMP_DIR`
- `IMAGE_SEARCH_MAX_CONCURRENCY`

模型文件、阈值配置和 Python 依赖必须锁定版本。密钥与 OSS/RAM 凭证遵循现有运行文档，不提交到 Git。

## 16. 已确认决策摘要

- 规模：少于 10,000 张。
- 首要目标：从模糊、压缩或局部图片精准找回图库原图。
- 部署：完全自托管。
- 延迟：MVP 接受约 3-8 秒。
- 算法：DINOv2 全图/局部向量召回，感知哈希与 SIFT 几何精排。
- 数据：PostgreSQL + pgvector 保存向量，OSS 保存版本化局部特征。
- 隐私：查询图片不持久化，不记录搜索历史。
- 生命周期：上传/替换预览异步索引，回收站隐藏、恢复复用、永久删除清理。
- 验收：以真实图库质量基准、生产 ECS P95 和跨用户隔离为发布门槛。
