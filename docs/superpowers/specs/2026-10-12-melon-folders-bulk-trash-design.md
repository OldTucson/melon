# Melon 文件夹、批量选择与回收站设计

**日期：** 2026-10-12

**状态：** 已确认，待实施

**适用范围：** Melon Web 图案库

**关联设计：** [Melon Web 产品与技术设计](2026-10-08-melon-web-design.md)

## 1. 摘要

本设计为 Melon 图案库增加三组相互关联的能力：

1. 完整的多选与批量操作，包括批量移动、收藏和移入回收站。
2. 嵌套文件夹系统，包括新建、重命名、查询和级联移入回收站。
3. 可恢复的回收站，包括单张图案恢复、文件夹删除批次整体恢复和永久删除。

图案采用唯一文件夹归属：一张图案最多属于一个文件夹，也可以暂时处于“未分类”。文件夹只是数据库中的组织元数据，不映射 OSS object key；移动或重命名文件夹不会复制 OSS 对象。

本设计修订基础设计中尚未实现的多选与回收站部分，并增加文件夹模型。基础设计中的认证、上传、预览、标签、下载、主题和租户隔离约束继续有效。

## 2. 已确认的产品决策

### 2.1 图案唯一归属

- `Pattern.folderId` 可为空。
- `folderId = null` 的活动图案显示在“未分类”。
- 将图案归类到另一个文件夹是移动，不是复制。
- 本规则只约束文件夹归属，不禁止用户上传内容相同的两个独立文件。
- 标签继续承担多维交叉分类；一个图案仍可拥有多个标签。

### 2.2 嵌套文件夹

- 文件夹可以包含子文件夹。
- 同一父文件夹下的活动或已回收文件夹名称不区分大小写且必须唯一。
- 根级文件夹之间执行相同的唯一性规则。
- 本阶段支持新建根文件夹、新建子文件夹和重命名。
- 本阶段不支持文件夹排序、拖拽重排、修改父级或智能文件夹。

### 2.3 删除父文件夹

删除文件夹是一次级联回收操作：

- 目标文件夹及其全部后代文件夹进入回收站。
- 文件夹子树中的所有图案进入回收站。
- 文件夹和图案共享同一个 `trashBatchId`。
- 子树中先前已单独回收的子文件夹或图案会合并到新的父级回收批次；已进入永久删除流程的实体会阻止本次操作。
- OSS 对象、资产记录、标签关系和未来的商业授权记录在保留期内保持不变。
- 回收站中该批次只能整体恢复，不能单独恢复其中的图案或子文件夹。
- 整体恢复后，原文件夹层级和图案位置保持不变。

普通的单张或多张图案删除同样生成一个 `trashBatchId`，但允许按图案选择性恢复。

### 2.4 永久删除

- 图案和文件夹默认保留 30 天。
- 用户可以在回收站中提前永久删除。
- 永久删除文件夹批次时，批次中的文件夹和图案一起永久删除。
- 只有永久删除阶段才清理 OSS 对象。
- 永久删除成功后保留最小数据库墓碑，阻止未来离线同步把旧数据复活。

## 3. 方案选择

### 3.1 采用：数据库虚拟文件夹

文件夹层级存储在 PostgreSQL 中，图案通过单个外键指向文件夹。优势：

- 移动和重命名只更新数据库。
- OSS object key 永久稳定。
- 回收、恢复和权限校验可以使用数据库事务完成。
- 与标签、筛选、商业授权和未来同步模型保持独立。

### 3.2 不采用：OSS 前缀映射文件夹

若把 OSS key 前缀当作文件夹，移动或重命名需要复制对象再删除旧对象。对于接近 100 MB 的 PSD、AI 和 Procreate 文件，这会增加延迟、费用和部分失败风险，并破坏已签发链接和上传断点。

### 3.3 不采用：图案与文件夹多对多

多对多模型更接近部分素材管理工具，但与本产品“每张图案只有一个位置”的确认规则冲突，也会使删除文件夹时的图案归属产生歧义。

## 4. 信息架构与交互

### 4.1 桌面布局

工作区采用紧凑的三栏布局，借鉴成熟素材管理软件的信息架构，但不复制其品牌视觉：

- 左栏：系统视图、嵌套文件夹树、标签、回收站和数据看板入口。
- 中栏：当前文件夹标题、筛选排序、批量操作栏和虚拟滚动素材墙。
- 右栏：单选详情检查器或多选批量检查器。

浅色模式以白色和中性灰为主，夜间模式使用近黑色表面；靛蓝只用于主操作和选中态。控件圆角不超过 6 px，页面区块不使用装饰性卡片。

### 4.2 文件夹树

- 文件夹行显示展开箭头、文件夹名称和递归图案总数。
- 当前文件夹使用安静的中性选中底色。
- 文件夹区标题右侧的加号创建根文件夹。
- 文件夹行上下文菜单提供“新建子文件夹”“重命名”“移入回收站”。
- 新建和重命名使用行内输入；保存失败时保留草稿并显示具体错误。
- 打开父文件夹时可切换“包含子文件夹内容”，默认开启。
- 删除前显示受影响的文件夹数和图案数。
- 如果子树中存在正在永久删除的实体，删除确认按钮禁用并要求先等待或重试该任务。

### 4.3 多选

- 普通单击只选择当前图案。
- `Command/Ctrl` 单击切换离散选择。
- `Shift` 单击选择当前排序下从锚点到目标的连续范围。
- 工具栏“全选”只选择客户端已经加载的结果，不隐式选择尚未分页加载的图案。
- 查询、文件夹或排序变化后清空选择，防止对不可见图案误操作。
- 选中项必须具有显式勾选标记，不能只依赖边框颜色。

存在选择时，中栏显示批量操作栏，右栏切换为批量检查器。首期批量动作：

- 移动到一个目标文件夹或“未分类”。
- 添加或取消收藏。
- 移入回收站。

批量标签编辑继续沿用既有标签组件，可在后续小版本接入，不阻塞本阶段交付。

### 4.4 图案删除

- 单张和批量删除都必须经过确认对话框。
- 确认后服务端原子更新全部图案；任何一项冲突则整批失败。
- 成功后从当前查询移除图案、清空对应选择并显示可撤销提示。
- 提示中的“撤销”调用恢复 API，不仅做客户端回滚。
- 回收站保留原 `folderId`，恢复后回到原文件夹。

### 4.5 文件夹级回收与恢复

- 文件夹删除确认框明确显示级联范围。
- 文件夹删除成功后导航到最近仍活动的祖先文件夹；若没有则进入“全部图案”。
- 回收站把文件夹删除显示为一个批次条目，展示根文件夹名称、文件夹数量、图案数量和到期日期。
- 恢复文件夹批次是原子操作；不能从批次中拆出单张图案。
- 文件夹名称在回收期间继续占用，保证恢复时不会出现同级名称冲突。

### 4.6 回收站

`/trash` 提供两类条目：

- 文件夹批次：整体恢复或整体永久删除。
- 图案批次：可选择其中部分图案恢复或永久删除。

正在永久删除的条目显示进行中状态，禁用恢复和重复操作。OSS 清理失败时显示可重试状态，不提前把条目标记为永久删除。

### 4.7 响应式行为

- Mac/桌面宽度优先显示完整三栏。
- iPad 宽度下左栏保持可用，右侧检查器可收起或显示在内容下方。
- 手机宽度下文件夹树改为抽屉，检查器改为底部面板；本阶段保证不溢出，但不把手机操作效率作为首要验收目标。

## 5. 数据模型

### 5.1 `folders`

新增 `folder_status`：

```text
active → trashed → deleting → deleted
           └────────恢复────────→ active
```

字段：

- `id uuid primary key`
- `ownerId uuid not null`
- `parentId uuid null`
- `name text not null`
- `normalizedName text not null`
- `status folder_status not null default active`
- `version integer not null default 0`
- `trashBatchId uuid null`
- `trashedAt timestamptz null`
- `deletedAt timestamptz null`
- `changeSeq bigint not null default 0`
- `createdAt timestamptz not null`
- `updatedAt timestamptz not null`

约束：

- `(ownerId, id)` 唯一，用于复合外键和租户隔离。
- `(ownerId, parentId)` 自引用 `(ownerId, id)`，禁止跨用户父子关系。
- `parentId != id`。
- 根级和非根级分别建立活动/回收名称唯一索引；只有 `deleted` 状态释放名称。
- `normalizedName` 使用 NFC 归一化后转小写。

本阶段不提供修改 `parentId` 的 API，因此应用层不会产生环。仓库层仍必须防止把非活动父级用于创建子文件夹。

### 5.2 `patterns` 扩展

新增字段：

- `folderId uuid null`
- `trashBatchId uuid null`
- `preTrashStatus pattern_status null`

新增状态：

- `deleting`

约束：

- `(ownerId, folderId)` 引用 `folders(ownerId, id)`。
- 活动图案只能引用活动文件夹或 `null`。
- 回收站图案保留原 `folderId`。
- 活动图案进入回收站时把原状态写入 `preTrashStatus`；合并已有回收批次时保留其既有原状态。
- `deleting` 和 `deleted` 图案不能恢复、移动、重命名或修改标签。
- 恢复成功后清空 `preTrashStatus`；永久删除墓碑不保留可恢复的原状态。

活动图库查询只包含业务状态为 `draft | hashing | uploading | processing | ready | failed` 的图案；回收站查询只包含 `trashed | deleting`。新增 `deleting` 后不能继续使用“仅排除 trashed/deleted”的宽松条件。

迁移时所有既有图案的 `folderId` 为 `null`，因此无数据搬迁风险。

### 5.3 回收批次

不新增独立批次表。成功的回收操作使用该请求的 `operationId` 作为 `trashBatchId`：

- 保持请求幂等。
- 可以把同一操作修改的文件夹和图案重新聚合。
- 文件夹批次根节点是批次内父级不属于该批次的文件夹。
- 到期时间由批次中最早的 `trashedAt + 30 天` 推导。

文件夹批次的恢复和永久删除按 `trashBatchId` 整体执行。普通图案批次允许对子集操作；已恢复的图案清空 `trashBatchId`。

### 5.4 变更日志

一次批量动作只分配一个 `changeSeq`，所有受影响行写入同一 `changeSeq`，并追加一条批次变更日志。载荷包含动作类型和受影响实体 ID，不包含长期签名 URL 或 OSS 凭证。

事件类型：

- `folder.created`
- `folder.updated`
- `folder_tree.trashed`
- `folder_tree.restored`
- `folder_tree.deleted`
- `patterns.moved`
- `patterns.trashed`
- `patterns.restored`
- `patterns.deleted`

## 6. API 与契约

### 6.1 文件夹 API

```text
GET    /api/folders
POST   /api/folders
PATCH  /api/folders/:folderId
DELETE /api/folders/:folderId
GET    /api/folders/:folderId/delete-impact
```

`GET /api/folders` 返回活动文件夹的扁平列表，每项包含 `parentId`、直接图案数和递归图案总数；客户端构建树。

创建请求：

```json
{
  "operationId": "uuid",
  "name": "夏日果园",
  "parentId": "uuid-or-null"
}
```

更新请求只允许修改名称并携带 `version`。删除请求携带 `operationId` 和 `version`，语义是级联移入回收站，不是 HTTP 层面的立即硬删除。

`delete-impact` 返回当前快照中的文件夹数、图案数、其中已经回收的数量以及是否存在 `deleting` 实体。真正删除时重新锁定和计算，不能信任预览结果。

### 6.2 图案查询

`GET /api/patterns` 增加：

- `folderId=uuid`
- `unfiled=true`
- `includeDescendants=true|false`
- `scope=library|trash`

`folderId` 与 `unfiled` 互斥。活动图库默认 `scope=library`；回收站页面使用专用的回收站服务聚合批次，不依赖普通图库分页完成分组。

### 6.3 批量图案 API

```text
POST /api/patterns/batch
```

请求使用判别联合：

```json
{
  "operationId": "uuid",
  "action": "move",
  "patterns": [{ "id": "uuid", "version": 3 }],
  "folderId": "uuid-or-null"
}
```

```json
{
  "operationId": "uuid",
  "action": "trash",
  "patterns": [{ "id": "uuid", "version": 3 }]
}
```

```json
{
  "operationId": "uuid",
  "action": "favorite",
  "patterns": [{ "id": "uuid", "version": 3 }],
  "isFavorite": true
}
```

约束：

- 每次 1 至 100 个唯一图案。
- 服务端验证所有图案属于当前用户。
- 服务端按 ID 稳定顺序锁行，避免批量操作互相死锁。
- 任一版本不匹配、状态不允许或目标文件夹无效时整体回滚。
- 移动到当前文件夹视为成功的幂等空操作，但仍返回服务器当前版本。
- `move`、`favorite` 和 `trash` 只接受当前可编辑状态；上传尚未完成的图案必须先通过上传队列取消，不能由批量图库操作隐式中断。

### 6.4 回收站 API

```text
GET  /api/trash
POST /api/trash/patterns/restore
POST /api/trash/patterns/purge
POST /api/trash/folder-batches/:trashBatchId/restore
POST /api/trash/folder-batches/:trashBatchId/purge
```

恢复和永久删除请求都携带新的 `operationId`。文件夹批次端点必须拒绝部分实体 ID；图案端点必须拒绝属于文件夹删除批次的图案，并返回 `FOLDER_BATCH_ACTION_REQUIRED`。

## 7. 服务端事务与并发

### 7.1 文件夹创建和重命名

- 创建子文件夹前锁定父文件夹，并验证父级是 `active`。
- 重命名前锁定目标文件夹并校验版本。
- 唯一索引是同级名称冲突的最终防线。
- 唯一冲突统一映射为 `FOLDER_NAME_CONFLICT`。

### 7.2 批量移动和删除图案

1. 声明并校验操作载荷。
2. 认领 `operationId`。
3. 按 UUID 排序锁定全部图案。
4. 验证所有权、版本和状态。
5. 移动时锁定目标文件夹并验证其活动状态。
6. 分配一个 `changeSeq`，更新全部图案并写入一条批次日志。
7. 保存幂等结果并提交。

### 7.3 级联回收文件夹

1. 认领 `operationId` 并锁定根文件夹。
2. 使用递归 CTE 解析尚未永久删除的完整子树，包括先前单独回收的后代。
3. 按 UUID 排序锁定子树中的全部文件夹。
4. 再次验证根版本，并拒绝包含 `deleting` 实体的操作。
5. 锁定 `folderId` 位于子树中的全部未永久删除图案，包括先前单独回收的图案。
6. 将文件夹和图案统一切换为 `trashed`；首次回收的图案记录 `preTrashStatus`，已经回收的图案保留原值。
7. 所有行写入相同 `trashBatchId = operationId` 和 `changeSeq`。
8. 写入批次日志和幂等结果后提交。

合并旧回收批次时统一使用本次操作时间作为新的 `trashedAt`，从而让整个父级批次拥有一致的 30 天恢复窗口。旧批次不再包含任何实体，后续查询忽略空批次。

创建子文件夹也会锁定父级，因此不能在级联回收事务计算完子树后并发插入漏网子节点。

### 7.4 恢复文件夹批次

1. 按 `trashBatchId` 锁定全部文件夹和图案。
2. 验证批次中不存在 `deleting` 或 `deleted` 实体。
3. 验证根文件夹的原父级仍为活动状态或为空。
4. 将全部文件夹恢复为 `active`，全部图案恢复为其回收前状态。
5. 清空 `trashBatchId` 和 `trashedAt`，递增版本并写入批次日志。

图案进入回收站前的状态保存在新增的 `preTrashStatus` 字段中，以便 `ready` 和 `failed` 图案都能准确恢复。文件夹只从 `active` 进入回收站，无需单独保存前态。

### 7.5 永久删除与 OSS

数据库事务不能覆盖 OSS 网络操作，因此永久删除采用可恢复的三阶段流程：

1. **认领：** 锁定目标，把图案和相关文件夹切换到 `deleting`，保存操作结果为进行中。
2. **清理：** 在事务外按最多 1000 个 key 分块调用 OSS 批量删除；对象已不存在视为成功。
3. **完成：** 重新锁定目标，删除资产和关联业务行，把图案、文件夹压缩为 `deleted` 墓碑并写入变更日志。

任何 OSS 调用失败都保留 `deleting` 状态和错误码。相同操作或后台清理器可以幂等重试；恢复接口拒绝 `deleting` 实体，从而避免 OSS 已删除但数据库又恢复的竞态。

现有 `operations.result` JSON 需要显式保存 `{ state: "pending" | "complete", ... }`。永久删除请求重放到 `pending` 时继续执行清理，而不是把空结果当作已成功；重放到 `complete` 时直接返回最终结果。后台清理器也会扫描 `deleting` 实体并按 `trashBatchId` 调用同一续跑函数，因此服务进程中断不会留下永久卡住的任务。

每日清理任务调用同一服务处理超过 30 天的 `trashed` 批次。部署前提供可独立运行的维护命令；托管环境只需定时触发该命令，不复制删除逻辑。

## 8. 客户端状态与缓存

- 文件夹查询使用独立的 React Query key：`folders(ownerId)`。
- 图案查询 key 包含 `folderId`、`unfiled` 和 `includeDescendants`。
- 文件夹新建和重命名可以乐观更新；冲突时回滚并保留输入。
- 批量移动可在当前结果中乐观移除图案，但必须保存完整查询快照用于失败回滚。
- 移入回收站和永久删除等待服务端确认后再移除，避免破坏性操作产生误导性成功状态。
- 成功的批量操作使文件夹计数、当前图案列表、图案详情和回收站查询失效。
- 选择状态只保存 ID，不跨查询持久化。

## 9. 错误处理

公开错误码：

- `FOLDER_NOT_FOUND`
- `FOLDER_NAME_CONFLICT`
- `FOLDER_STATE_CHANGED`
- `FOLDER_NOT_ACTIVE`
- `PATTERN_STATE_CHANGED`
- `BATCH_LIMIT_EXCEEDED`
- `FOLDER_BATCH_ACTION_REQUIRED`
- `TRASH_BATCH_NOT_FOUND`
- `TRASH_PURGE_IN_PROGRESS`
- `OSS_DELETE_FAILED`

客户端行为：

- `409` 状态冲突：刷新文件夹树和当前图案查询，保留非破坏性表单草稿。
- 名称冲突：输入框原位显示错误，不关闭编辑状态。
- 批量冲突：不保留部分客户端成功状态，显示“图库已发生变化，请重新选择”。
- OSS 删除失败：条目保留在回收站并显示“删除失败，可重试”。
- 网络中断：不重复生成 `operationId`，重试原请求。

## 10. 安全与数据隔离

- 所有仓库查询都同时限定 `ownerId` 和实体 ID。
- 文件夹父级、图案文件夹外键都使用包含 `ownerId` 的复合外键。
- 服务端忽略客户端提供的计数、层级路径和所有者信息。
- 删除影响预览只是提示；执行阶段必须重新计算并锁定真实范围。
- OSS 删除只使用数据库中属于当前用户目标图案的 object key。
- 日志不记录 STS 凭证、签名 URL、AccessKey 或源文件内容。

## 11. 测试策略

### 11.1 单元测试

- 文件夹名称归一化和请求契约。
- 批量请求去重、数量上限和判别联合。
- 文件夹树构建、展开状态和递归计数显示。
- 多选、连续选择、全选已加载结果和查询变化清空。
- 批量操作栏、确认对话框和错误状态。

### 11.2 PostgreSQL 集成测试

- 同级名称唯一性和不同父级同名。
- 跨租户父子关系、图案归属和批量 ID 注入被拒绝。
- 新文件夹、重命名和父级非活动校验。
- 批量移动全部成功或全部回滚。
- 级联文件夹回收包含全部后代和图案。
- 文件夹批次整体恢复保持原层级和图案位置。
- 文件夹批次中的图案不能单独恢复。
- 普通图案批次允许部分恢复。
- 并发创建子文件夹与级联回收不会留下活动孤儿。
- 幂等重放返回原结果，复用不同载荷返回冲突。

### 11.3 OSS 与永久删除测试

- Fake OSS 覆盖成功、对象不存在、分块删除和中途失败重试。
- 数据库只在全部 OSS 删除成功后进入 `deleted`。
- `deleting` 状态禁止恢复。
- 真实 OSS 冒烟测试只创建并清理测试前缀中的对象。

### 11.4 E2E

至少覆盖：

1. 新建根文件夹和子文件夹。
2. 重命名文件夹并验证名称冲突。
3. 多选图案并移动到唯一目标文件夹。
4. 删除父文件夹，验证子树和图案进入回收站。
5. 整体恢复文件夹批次，验证层级和图案位置。
6. 批量删除图案并恢复其中一部分。
7. 浅色、夜间模式以及桌面和 iPad 宽度无溢出。

## 12. 迁移与交付顺序

1. 新增文件夹 schema、图案字段和迁移；既有图案保持未分类。
2. 实现文件夹仓库、服务、契约和 API。
3. 扩展图案查询和批量事务服务。
4. 实现文件夹树、批量栏和唯一目标文件夹选择器。
5. 实现回收站查询、恢复和撤销。
6. 实现永久删除状态机、Fake OSS 测试和清理命令。
7. 完成桌面/iPad E2E、视觉校验、文档和部署说明。

每一步先补失败测试，再实现最小通过代码；数据库迁移在实现进入主分支前必须在空库和现有开发库各验证一次。

## 13. 验收标准

1. 一张活动图案最多属于一个活动文件夹，且允许未分类。
2. 用户可以新建根文件夹、创建子文件夹、重命名和删除文件夹。
3. `Command/Ctrl`、`Shift` 和“全选已加载项”行为一致且可访问。
4. 批量移动、收藏和移入回收站不会产生部分成功。
5. 删除父文件夹会把完整子树和其中图案放入同一回收批次。
6. 文件夹批次只能整体恢复，并恢复原层级及图案位置。
7. 永久删除前 OSS 文件保持不变；永久删除失败可幂等重试。
8. 所有文件夹和批量 API 保持租户隔离并验证版本。
9. 图库保持紧凑三栏布局，支持浅色和夜间模式，在 iPad 宽度不发生控件重叠或文本溢出。
10. 单元、集成、OSS 和 E2E 验证全部通过。
